## ① β版終了の人数判断

**結論: 初回仕事を完了した実ユーザー 50人でβ終了候補。同時招待枠は最大20人。**

| 項目 | 数値 | 理由 |
|------|------|------|
| 同時β招待 | 10–20人 | Phase5どおり。サポートと観察が壊れない上限 |
| β終了の母数 | **初回完了ユーザー ≥ 50** | Phase6公開判定の最低サンプルと一致。感覚で「もういい」と言わない |
| β終了の条件 | `/owner/launch-verdict` = 🟢 | 人数だけでは終了しない。数字が公開基準を満たすこと |
| 入れ替え | 14日無利用は招待枠を空ける | 枠20を死蔵しない |

運用: 20人枠で回しつつ、完了ユーザーの累計が50に達し、かつ公開判定🟢になった時点でβ終了→正式公開。  
**50未満・🟡/🔴のまま人数だけ増やすのは禁止。**

## ② 正式公開後、最初の100人をどう獲るか（広告費最小）

**原則: 広告を買わない。終わった仕事が営業する。**

### 他社の「最初の100」の型（考え方だけ借りる）

| 会社 | 最初の広げ方の本質 | MINERVOTへの翻訳 |
|------|-------------------|------------------|
| OpenAI | 研究・デモを見た人が自分で試す | 「写真→資料が開く」実物を1回見せる。説明会を増やすな |
| Notion | テンプレと個人の公開ページが伝播 | **完成したWord/資料そのもの**が社内・取引先に渡る |
| Cursor | 開発者が成果（速度）をSNSで見せる | 忙しい個人が「資料作りが消えた」と一言で伝える |
| Linear | 招待制の密度＋意見リーダー | β20の質を落とさず、紹介枠だけ開ける |
| Canva | 非デザイナーが作った絵が共有される | 非・資料職が作った資料が会議に出る |
| Slack | チームの片側が入れ、相手も入る | 依頼者と受け取り手（上司・顧客）の非対称導入 |
| Figma | ファイル共有がアカウントを生む | **成果物リンク/ファイル転送が招待になる** |

### MINERVOTの100人獲得プレイブック（広告ほぼゼロ）

1. **シード20（β卒業生）**  
   すでに完了経験がある人だけ残す。未完了は数に入れない。

2. **成果物転送（主エンジン）**  
   完了画面のあと、ユーザーがやることはもともと「開く／渡す」。  
   運営がやることは一つだけ: 完了した人に  
   「その資料を渡した相手が困るなら、同じ依頼をMINERVOTに投げてと一言添えてください」  
   を**手動で**伝える（自動キャンペーン機能は作らない）。

3. **職能コミュニティへの実物投下（週5件まで）**  
   営業事務・個人事業・士業補助・店舗オーナーなど「資料作成が習慣作業」の場に、  
   完成物のスクショではなく**「依頼文一文＋所要時間」**だけ置く。製品宣伝ページを量産しない。

4. **逆紹介のお願い（完了3回目の人だけ）**  
   3回仕事が終わった人にだけ、知人1名を紹介してもらう。  
   1回目では頼まない（まだ信頼が薄い）。

5. **広告**  
   最初の100人までは**出さない**。100人到達後も、週次3指標がすべて前週比で伸びているとき以外は出さない。

**100人の定義:** 初回仕事完了ユーザーの累計100（登録だけは数えない）。

## ③ 100 → 1,000 → 10,000 ロードマップ

新機能なし。チャネルと運用密度だけ変える。

### Stage A: 100人（密度）

| 見るもの | 目標イメージ |
|----------|----------------|
| 週次仕事完了ユーザー | 安定して増える |
| 紹介経由の新規完了 | 新規の過半数に近づける |
| 有料ユーザー | 小さくてよい。無理売り禁止 |

やること: 手動紹介依頼、成果物転送の習慣化、壊れている完了率だけ直す（GrowthではなくPhase6改善ルール）。

### Stage B: 1,000人（ループ）

| レバー | 中身（機能追加ではない） |
|--------|---------------------------|
| 紹介ループ | 完了3回ごとに「1人紹介」を運用で徹底 |
| 職能クラスター | 同じ職種の塊を1つずつ飽和（横展開しすぎない） |
| チーム非対称 | 資料の受け手側に「次もこれで」と頼む文面をユーザーが自分で送るのを助ける（テンプレ文章の運用。製品機能化しない） |
| 有料 | 毎週使う人にだけ980円の価値を口頭/メールで説明する |

止めこと: 機能ロードマップ会議、ブランド刷新、広告予算の先出し。

### Stage C: 10,000人（再現）

| レバー | 中身 |
|--------|------|
| 紹介の自律化 | 運営が頼まなくても成果物転送で入る状態か、週次で検証 |
| 地域/言語 | 日本語で勝ち切ってから次。同時多言語は成長を薄める |
| 有料LTV | 解約理由を数字で分類し、**悪い数字の原因だけ**運用で潰す |
| 採用 | サポートとオンボーディング運用の人手。エンジニアの機能開発ではない |

**ステージ遷移条件（感覚禁止）**

- 100→1000: 直近4週、紹介経由の新規完了が新規完了の **≥40%**、かつ週次仕事完了ユーザーが前週比で概ね非減少
- 1000→10000: 同上 **≥50%**、かつ有料の純増が4週連続で非負

## ④ 紹介したくなる仕組み（既存価値のみ）

紹介の本質は「自分が楽になった証拠を、同じ痛みの知人に渡すこと」。

1. **証拠がファイルである** — チャット履歴ではなく、渡せる資料が残る（既存）  
2. **説明不要** — 「この写真を資料にして」で再現できる（既存の初回体験）  
3. **紹介タイミング** — 完了直後と3回目完了時だけ依頼する（運営ルール）  
4. **紹介の見返りは機能ではない** — クレジット乱発でLTVを壊さない。必要なら「紹介された人が初回完了したら、紹介者のサポート優先」程度の運用  
5. **恥をかかない品質** — 紹介率より先に仕事完了率・初回成功率（Phase6）。品質が落ちたら紹介施策を止める

---

## ⑤ 解約率を下げる仕組み（既存価値のみ）

解約は「秘書が仕事を終わらせなくなった」か「毎週の用事がなくなった」ときに起きる。

1. **完了率・エラー率を公開基準以上に保つ**（最重要。新UIより先）  
2. **解約前に聞くのは一文だけ** — 「最後に終わらなかった仕事は何ですか？」→ その仕事タイプの失敗だけ直す  
3. **使っていない人に新機能を案内しない** — 沈黙を機能で埋めない  
4. **課金説明は週次利用者に限定** — 月1しか使わない人を無理に残さない（LTVの錯覚を避ける）  
5. **失敗した依頼の再実行を簡単にする既存導線だけ磨く**（コピー追加や導線整理は可。新製品領域は不可）

## ⑥ 毎日使う理由

MINERVOTはSNSではない。**毎日の定義を「開く」ではなく「今日の仕事が1件終わる」にする。**

毎日使う理由（既存価値）:

- 毎日発生する小さい資料・写真・メモの片付けがある職種にだけ深く刺す  
- 朝いちの「今日終わらせる1件」をMINERVOTに投げられる（習慣は職種選定で作る。機能で作らない）  
- チャット履歴を育てる快感を狙わない。**完了の快感だけ**を残す

毎日使わない職種を無理にデイリー化しない。週次でもLTVが出るならそれでよい。

---

## ⑦ 毎週戻ってくる理由

週次の習慣作業と同期させる。

- 週報・請求・報告書・会議資料など、**週1の痛み**を持つユーザーを優先セグメントにする  
- 週の初めに「先週と同じ種類の仕事」がまた来るなら、前回の完了体験が再訪理由になる  
- 再訪KPIは Phase6 の7日継続を成長期も監視し、Growth OSの3指標と矛盾させない

## ⑧ 980円以上払いたくなる理由

払う理由は「AIがすごい」ではない。**自分の時間が毎週戻ってくるから。**

| 条件 | 目安 |
|------|------|
| 週の節約時間 | 資料作成が週30分以上消えている実感（ユーザーの自己申告ではなく、週次完了回数で代理） |
| 代替コスト | 外注・残業・手作業より明らかに安い |
| 失敗コスト | 有料でも完了率が公開基準以上（失敗する秘書に金は払わない） |
| 説明 | 「チャットし放題」ではなく「仕事が終わる回数」で価値を語る |

980円は、**週2回以上仕事が完了しているユーザー**にだけ真剣に勧める。それ未満は無料のままでよい。

## CEOが見る指標は3つだけ

| # | 指標 | 定義 | なぜこれだけか |
|---|------|------|----------------|
| 1 | **週次仕事完了ユーザー** | 直近7日で≥1件 `complete` したユニークユーザー | 使われているかの真実。登録者数は嘘をつく |
| 2 | **紹介→初回完了** | 直近7日の初回完了のうち、紹介経由と判定できる割合 | 広告なしで増えるかの真実 |
| 3 | **有料ユーザー数（純）** | 現在の有料サブスク数 | LTVの土台。収益なき成長は自殺 |

**見ないもの（禁止）:** DAU虚栄、機能リリース数、SNSいいね、ページビュー、NPS単独、AIトークン消費量。

週次レビュー手順:

1. `/owner/growth-os` を開く  
2. 3指標の前週比を見る  
3. 落ちた指標に対応する運用だけ変える（④⑤⑥⑦⑧の該当節）  
4. 伸びている指標には触らない

## 5年後、世界中で使われるサービスになるとしたら — 最も重要だった意思決定（1つ）

**「成功の定義を、機能数でもモデルの賢さでもなく、終わった仕事が他人に渡った回数に固定したこと。」**

それ以外（ブランド、モデル切替、機能競争）は、この定義を守れた場合にだけ後から効く。
